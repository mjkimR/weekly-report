# 스킬 명세

`SKILL.md` 세 개를 쓰기 위한 설계. 각 스킬이 언제 불리고, 무엇을 받고, 어떤 순서로 움직이고, 무엇을 남기는지 정한다.

CLI 호출은 [contract.md](contract.md) 에 정한 것만 쓴다.

## 공통 규약

**프론트매터.** `name` 과 `description` 을 항상 둘 다 넣는다. Claude Code는 `name` 이 없으면 디렉토리 이름을 쓰지만, Gemini CLI는 둘 중 하나라도 없으면 스킬을 조용히 건너뛴다. 구분선 `---` 앞에 아무 텍스트도 오면 안 된다.

`allowed-tools`, `disable-model-invocation`, `argument-hint`, `$ARGUMENTS` 는 Claude Code 확장이다. 넣어도 다른 에이전트가 무시하니 해롭지 않지만, 그 기능이 있다고 가정한 설계는 하지 않는다. 인수는 치환에 기대지 말고 사용자 발화에서 읽는다. 어차피 에이전트는 사용자가 뭘 말했는지 보고 있다.

**본문 길이.** 스킬이 로드되면 그 턴 내내 컨텍스트에 남는다. 배경 설명을 쓰지 말고 할 일만 쓴다. 긴 참고 자료는 같은 디렉토리의 별도 파일로 빼서 필요할 때만 읽게 한다.

**시작 확인.** 세 스킬 모두 `command -v uv` 로 시작한다. 없으면 설치를 안내하고 멈춘다.

**실패 처리.** 종료 코드 2가 나오면 `weekly-report-onboard` 를, 3이 나오면 `weekly-report-repos` 를 안내한다. 스킬이 설정 파일을 직접 고쳐서 문제를 우회하지 않는다.

**경고 표시.** CLI의 `warnings` 는 canonical English다. 사용자에게 보여주기 전에 최신 요청의 언어로 번역하고 날짜, 파일 경로, 명령, 기술 식별자는 원문 그대로 보존한다. 요청 언어가 불분명하면 영문 원문을 쓴다.

## `weekly-report`

주간보고 한 번을 처리한다. 평소에 쓰는 스킬은 이것뿐이다.

**description.** 이번 주 주간보고를 작성한다. Git 커밋을 모아 초안을 만들고 사용자가 고칠 파일을 넘긴다. "주간보고", "주간 리포트", "이번 주 한 일 정리" 같은 요청에 쓴다.

**순서**

1. `weekly-report run --json` 실행
2. 종료 코드가 0이 아니면 표에 따라 처리하고 멈춘다
3. `period.since_source` 가 `fallback_7d` 면 구간이 최근 7일로 잡혔다고 알리고 계속할지 묻는다
4. `warnings` 가 있으면 공통 경고 표시 규약에 따라 번역해 전한다
5. `paths.prompt` 파일을 읽는다
6. 프롬프트의 지시에 따라 리포트를 쓴다. 형식은 `template.md`, 문체와 표현은 프롬프트에 들어 있는 지난 리포트를 따른다
7. 사용자가 이번 주 특이사항을 함께 말했으면 그 내용도 반영한다
8. `paths.report` 에 리포트를 쓴다. 다른 곳에 쓰지 않는다
9. 사용자에게 알린다

**7단계: 추가 컨텍스트**

커밋에 안 드러나는 일이 있으면 사용자가 스킬을 부를 때 같이 말한다. 회의, 문서 작업, 남에게 넘긴 일 같은 것들이다. 별도 메모 파일은 없다. 에이전트는 이미 사용자 발화를 보고 있으니 그대로 반영하면 된다.

CLI에 넘길 필요도 없다. 프롬프트는 Git 기록만 담고, 추가 컨텍스트는 리포트를 쓰는 시점에 얹는다.

**9단계에서 알릴 것**

- 수집 구간과 저장소별 커밋 수 한 줄 요약
- `paths.report` 절대 경로
- 토큰 어림값은 임계값을 넘었을 때만
- 근사 경계 경고가 있으면 최종 응답에도 다시 넣고, 생성한 초안에서 중복 항목을 검수하라고 안내

리포트 본문을 대화창에 붙이지 않는다. 사용자는 파일을 열어서 읽고 고친다. `할 일` 처럼 커밋에서 알아낼 수 없는 항목은 어차피 손을 보게 되니, 수정을 대화로 주고받지 않고 파일을 넘기는 게 이 스킬의 목적이다.

**주의**

- `run` 은 이미 파일을 정리했다. 이전 리포트를 아카이브하고 빈 `report.md` 를 만들어 둔 상태다. 스킬이 그 정리를 다시 하려 들면 안 된다
- 실행을 두 번 하면 안 된다. 두 번째 실행이 방금 만든 빈 `report.md` 를 지우고 구간을 다시 계산한다
- 프롬프트가 지난 리포트를 담고 있으니, 지난 리포트를 따로 읽을 필요가 없다

## `weekly-report-onboard`

처음 설정한다. 기존 리포트를 몇 개 받아서 형식과 문체를 역산하고, 설정과 히스토리를 만든다.

**description.** 주간보고 스킬을 처음 설정한다. 기존에 쓰던 리포트를 몇 개 받아서 형식과 언어를 알아내고, 대상 저장소와 작성자를 정한다. "주간보고 설정", "온보딩", 처음 쓰기 시작할 때 쓴다.

**순서**

1. `weekly-report run --json` 으로 상태를 본다. 종료 코드가 2가 아니면 설정이 이미 있다는 뜻이다. 덮어쓸지 물어보고, 아니라면 멈춘다
2. 기존 리포트를 받는다. 붙여넣기도 되고 파일 경로도 된다. 2개 이상 5개 이하가 적당하다고 안내한다. 하나도 없으면 기본 템플릿으로 시작한다
3. 아래 체크리스트대로 형식을 역산한다
4. `template.md` 초안을 보여주고 확인받는다
5. 대상 저장소를 정한다
6. `weekly-report authors <경로>...` 로 작성자를 정한다
7. `config.yaml` 을 쓴다
8. 받은 리포트를 `history/` 에 심는다
9. `weekly-report run --dry-run --json` 으로 검증한다

### 3단계: 형식 역산 체크리스트

받은 리포트에서 다음을 뽑는다. 추측한 것은 4단계에서 사용자에게 확인받는다.

| 항목 | 보는 것 | 예 |
| --- | --- | --- |
| 언어 | 본문에 쓰인 언어 | `korean` |
| 제목 형식 | 첫 줄의 날짜 표기 | `# 7/23`, `# 2026/07/23`, `# 2026-07-23 주간보고` |
| 섹션 제목 | 최상위 제목과 그 순서 | `## 한 일`, `## 할 일` |
| 계층 깊이 | 목록이 몇 단까지 들어가는지 | 4단 (분류 → 하위 분류 → 항목 → 세부) |
| 분류 축 | 최상위 항목을 나누는 기준 | 저장소별, 업무 영역별, 둘을 섞은 형태 |
| 문체 | 문장 종결 방식 | 명사형 종결, 완전한 문장, 개조식 |
| 항목 길이 | 한 항목이 보통 몇 자인지 | 30~80자 |
| 괄호 관례 | 부연을 어떻게 붙이는지 | `기능 추가 (호환성 대응)` |

`template.md` 는 실제 내용이 아니라 자리표시자로 쓴다. 지금 형식(`{main_category_1}`, `{item_1}`)을 유지한다. 계층 깊이와 섹션 제목이 형식의 핵심이고, 문체와 항목 길이는 프롬프트에 들어가는 지난 리포트가 알려준다.

분류 축을 잘못 잡으면 매주 티가 난다. 저장소가 여러 개일 때, 최상위를 저장소로 나눈 리포트와 업무 영역으로 나눈 리포트는 완전히 다르게 읽힌다. 그래서 이 항목은 반드시 확인받는다.

### 5단계: 대상 저장소

현재 작업 디렉토리가 Git 저장소면 후보로 제안한다. 확인 없이 넣지 않는다. 스킬을 전역으로 깔면 아무 프로젝트에서나 실행되므로, 자동으로 넣으면 남의 저장소가 리포트에 섞인다.

그다음 다른 저장소 경로를 묻는다. 보통 여러 개를 쓴다. 표시 이름은 경로 마지막 조각을 기본값으로 제안하되, 리포트에 그 이름이 그대로 나온다고 알려준다.

### 6단계: 작성자

`weekly-report authors` 결과를 보여준다. 저장소마다 커밋 이름이 다를 수 있고, `git config user.name` 과 실제 커밋 이름이 어긋날 수도 있다. 이 단계에서 그걸 잡는다.

모든 저장소에서 같은 이름을 쓰면 전역 `author` 하나로 끝낸다. 갈리는 저장소가 있으면 그 저장소에만 `authors` 를 붙인다.

### 8단계: 히스토리 심기

**이 단계를 빼먹으면 온보딩이 끝나지 않는다.** `history/` 가 다음 수집 구간의 시작점을 정하는 유일한 기록이라, 비어 있으면 첫 실행이 최근 7일로 떨어진다.

날짜는 사용자에게 묻는다. 파일 내용에서 추측하지 않는다. 리포트 제목에 연도가 없는 경우가 많고, 틀린 날짜는 다음 수집 구간을 조용히 어긋나게 만든다.

가장 최근 리포트의 날짜 하나만 물어보고 나머지는 7일씩 거슬러 올라가는 것으로 충분하다. 주간보고는 보통 주 단위로 규칙적이다.

```
weekly-report history import 최신.md 그전.md 그전전.md --weekly-from 2026-07-23 --json
```

간격이 불규칙하다고 하면 `weekly-report history import 리포트.md --date 2026-07-23 --json` 처럼 파일별로 하나씩 넣는다.

날짜만으로는 정확한 cutoff 시각을 알 수 없으므로 CLI는 경계 날짜를 `00:00:00` 으로 기록한다. 경계 날짜의 커밋을 누락하지 않는 대신 첫 수집이 기존 리포트와 겹칠 수 있다. import와 검증 dry-run의 근사 경계 경고는 예상된 결과이며 온보딩 실패가 아니다.

### 9단계: 검증

`run --dry-run --json` 을 돌려서 확인한다.

- `period.since_source` 가 `history` 인지. `fallback_7d` 면 8단계가 잘못된 것이다
- `period.since` 가 마지막 리포트 날짜와 맞는지
- 저장소별 커밋 수가 0이 아닌지. 0이면 작성자 이름을 잘못 잡았을 가능성이 크다
- 토큰 어림값이 임계값 아래인지. 넘으면 `max_diff_lines` 를 줄이라고 안내한다

마지막에 설정 파일과 상태 디렉토리 경로를 알려주고, 다음부터는 `weekly-report` 를 쓰면 된다고 말한다. 근사 경계 경고를 최신 요청의 언어로 함께 알리고 첫 초안의 중복 항목을 검수하도록 안내한다. 온보딩에서 리포트를 만들지는 않는다.

## `weekly-report-repos`

대상 저장소 목록을 보고, 추가하고, 제거한다.

**description.** 주간보고가 훑는 Git 저장소 목록을 관리한다. 저장소를 추가하거나 제거하거나 현재 목록을 확인할 때 쓴다.

**순서**

사용자가 무엇을 원하는지 판단해서 해당 명령을 부른다. 인수 치환에 기대지 않고 발화에서 읽는다.

| 요청 | 부를 것 |
| --- | --- |
| 목록 확인 | `weekly-report repo list --json` |
| 추가 | `weekly-report repo add <경로> [--name] [--author]` |
| 제거 | `weekly-report repo remove <이름 또는 경로>` |

**추가할 때**

- 경로를 안 줬으면 현재 디렉토리를 후보로 제안하고 확인받는다. 확인 없이 넣지 않는다
- 하위 디렉토리를 줬으면 CLI가 저장소 루트를 찾아 저장한다. 어느 경로로 저장되었는지 알려준다
- CLI가 "최근 커밋 없음" 경고를 내면 그대로 전하고, 작성자 이름을 확인할지 묻는다. 여기서 넘기면 매주 조용히 0건이 된다
- 표시 이름이 리포트에 그대로 나온다고 알려준다

**제거할 때**

무엇을 지웠는지 확인해서 알려준다. `history/` 는 건드리지 않는다. 지난 리포트에 그 저장소 내용이 남아 있는 것은 정상이다.
