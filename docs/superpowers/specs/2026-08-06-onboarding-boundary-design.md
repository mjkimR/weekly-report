# 온보딩 날짜 경계 보완 설계

## 배경

`weekly-report history import`는 기존 보고서의 날짜만 입력받고 저장 시각을
`09:00:00`으로 고정한다. 기존 보고서가 실제로 어느 시각까지의 커밋을 포함했는지는
온보딩 시점에 알 수 없으므로, 임의 시각을 정확한 수집 경계처럼 취급하면 첫 보고서에서
커밋이 누락되거나 중복될 수 있다.

이 설계는 최초 수집에서 중복보다 유실 방지를 우선한다. 날짜만 아는 경계는 해당 날짜의
시작 시각으로 넓히고, 첫 보고서에만 중복 가능성을 명확히 안내한다. 이후 주간 사이클은
기존 `created` 마커의 초 단위 경계를 그대로 사용한다.

## 목표

- date-only 온보딩으로 인해 경계일의 커밋이 누락되지 않게 한다.
- 경계가 부정확하다는 사실을 상태에 기록하고 첫 보고서 생성 시 사용자에게 알린다.
- 첫 보고서 이후에는 정확한 `created` 시각으로 자동 전환하고 경고를 반복하지 않는다.
- CLI 경고 원문은 영어로 유지하고, 스킬이 사용자의 요청 언어로 번역한다.
- 기존 히스토리와 정상 주간 사이클의 동작을 깨지 않는다.

## 비목표

- 온보딩 중 경계일의 마지막 포함 커밋을 사용자에게 선택하게 하지 않는다.
- 기존에 `09:00:00`으로 가져온 히스토리를 자동 마이그레이션하지 않는다.
- 이번 변경에서 정확한 타임스탬프용 별도 CLI 옵션을 추가하지 않는다.
- 커밋 해시 원장을 도입하거나 Git 수집 모델 전체를 변경하지 않는다.

## 상태 표현

date-only로 가져온 각 보고서는 해당 날짜의 `00:00:00`으로 저장한다. 가져온 보고서
내용의 첫 줄에는 다음 bookkeeping 마커를 추가한다.

```text
[//]: # (weekly-report: boundary approximate date-only)
```

마커는 `history/` 안의 보고서와 함께 이동하는 영속 상태다. 별도 상태 파일을 만들지
않으므로 `history/`가 유일한 상태 저장소라는 기존 설계를 유지한다.

과거 보고서를 프롬프트에 포함할 때는 기존 `created` 마커 및 placeholder와 함께 이
마커도 제거한다. 따라서 사용자 보고서 형식과 모델 출력에는 bookkeeping 정보가 섞이지
않는다.

마커가 없는 기존 히스토리는 현재와 같이 정확한 경계로 취급한다. 과거 데이터만 보고
경계의 정확도를 추측하지 않는다.

## 데이터 흐름

### 온보딩 import

1. 사용자는 현재와 같이 최신 보고서의 날짜만 제공한다.
2. `history import --date` 또는 `--weekly-from`은 날짜를 `00:00:00`으로 정규화한다.
3. 가져온 보고서에 approximate 마커를 추가한다.
4. import 결과의 `warnings`에 아래 canonical 영어 경고를 포함한다.

> Onboarding only knows the imported report's date, not its exact cutoff time. To avoid missing commits, the first collection includes the entire boundary day ({date}). Some work may overlap with the imported report, so please review the generated draft for duplicate items.

`{date}`에는 실제 최신 경계일을 `YYYY-MM-DD` 형식으로 넣는다.

### 첫 `weekly-report run`

1. 최신 알려진 보고서가 approximate 마커를 가졌는지 확인한다.
2. 경계일 `00:00:00`부터 커밋을 수집한다.
3. 동일한 canonical 영어 경고를 `run --json`의 `warnings`에 포함한다.
4. 드라이런은 상태를 변경하지 않으므로 다음 실제 실행에서도 경고가 유지된다.
5. 커밋이 없어서 보고서를 만들지 않은 경우에도 approximate 상태와 경고가 유지된다.

### 첫 보고서 이후

에이전트가 새 `report.md`를 작성하면 정확한 `created` 마커가 최신 경계가 된다. 다음
실행은 이 초 단위 시각을 사용하므로 approximate 히스토리가 남아 있어도 경고하지 않는다.
새 보고서가 아카이브된 뒤에도 같은 정확한 시각이 파일명에 보존된다.

## 경고 번역과 사용자 전달

CLI의 `warnings` 값은 API 계약과 테스트 안정성을 위해 항상 영어로 유지한다.

`weekly-report`와 `weekly-report-onboard` 스킬에는 다음 지침을 추가한다.

- 사용자에게 경고를 전달할 때 최신 사용자 요청의 언어로 자연스럽게 번역한다.
- 날짜, 파일 경로, 명령어, 기술 식별자는 원문 그대로 보존한다.
- 요청 언어를 판단하기 어려우면 영어 원문을 사용한다.
- approximate 경계 경고는 최종 파일 안내에도 다시 포함한다. 중간 commentary가 접혀도
  사용자가 중복 검수 필요성을 놓치지 않아야 한다.

한국어 요청에서는 다음과 같은 의미로 전달한다.

> 온보딩에서는 가져온 이전 보고서의 날짜만 알 수 있고 정확한 마감 시각은 알 수 없습니다. 커밋이 누락되지 않도록 최초 수집에는 경계일(2026-07-30) 하루 전체를 포함했습니다. 이전 보고서와 겹치는 작업이 있을 수 있으니 생성된 초안에서 중복 항목을 확인해 주세요.

번역문 자체를 코드에 저장하지 않는다. 스킬이 canonical 영어 경고의 의미를 보존하여
요청 언어에 맞게 번역한다.

## 오류 처리와 호환성

- source 파일 누락, 날짜 형식 오류, 기존 destination 충돌 등 현재 import 실패 동작은
  유지한다.
- import 중 실패하면 해당 파일에 approximate 마커가 없는 불완전한 복사본을 남기지
  않는다.
- 기존 `09:00:00` 히스토리는 마커가 없으므로 이름과 수집 경계를 변경하지 않는다.
- `created` 마커가 있는 정상 보고서는 approximate 경고 대상이 아니다.
- approximate 마커가 최신 경계가 아닌 경우 경고하지 않는다.
- `warnings` 배열 외의 JSON 스키마와 종료 코드는 변경하지 않는다.

## 테스트 설계

### 단위 테스트

- approximate 마커를 추가하고 감지할 수 있다.
- `strip_report_marks`가 approximate 마커를 제거하고 보고서 본문은 보존한다.
- marker가 없는 기존 보고서는 exact로 분류한다.
- 최신 exact 보고서가 approximate 히스토리보다 최신이면 경고 대상이 아니다.

### 통합 테스트

- `history import --date`가 `00:00:00` 파일명과 approximate 마커를 만든다.
- `--weekly-from`으로 가져온 모든 보고서가 날짜별 `00:00:00`과 마커를 가진다.
- import JSON은 최신 경계일이 포함된 canonical 영어 경고를 반환한다.
- 첫 dry-run과 첫 실제 run 모두 경고하며, dry-run은 상태를 소비하지 않는다.
- 커밋이 없는 run 이후에도 다음 run에서 경고한다.
- 첫 보고서를 채운 뒤 다음 run에서는 경고가 사라지고 `created` 시각부터 수집한다.
- 기존 marker 없는 히스토리는 종전과 동일하게 동작한다.

### 스킬 검증

- 두 스킬이 CLI 경고를 사용자 요청 언어로 번역하도록 명시한다.
- 날짜와 기술 식별자를 번역 중 변경하지 않도록 명시한다.
- `weekly-report` 최종 응답에 approximate 경계 경고를 반복하도록 명시한다.

## 완료 조건

- date-only import의 최신 경계가 해당 날짜 `00:00:00`이다.
- 최초 수집에서 경계일 커밋이 누락되지 않는다.
- approximate 상태가 첫 보고서 생성 전까지 유지된다.
- 첫 보고서 이후 정확한 초 단위 경계로 전환되고 경고가 사라진다.
- CLI는 친절한 canonical 영어 경고를 반환한다.
- 스킬은 경고를 사용자 요청 언어로 번역해 최종 응답에도 포함한다.
- 기존 히스토리, JSON 스키마, 종료 코드와 정상 주간 사이클이 호환된다.
