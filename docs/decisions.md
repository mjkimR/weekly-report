# 설계 결정 기록

이 프로젝트를 에이전트 스킬로 전환하면서 정한 내용과 이유. 2026-07-30 기준.

나중에 "왜 이렇게 했지"를 다시 논의하지 않으려고 남긴다. 결정을 뒤집을 때는 여기 적힌 근거를 먼저 읽고, 그 근거가 아직 유효한지 확인한다.

## 1. 배포는 평범한 SKILL.md로 한다

Claude Code 플러그인 형식을 쓰지 않는다. 스킬 디렉토리에 `SKILL.md` 를 두고, `npx skills add mjkimR/weekly-report` 로 설치한다.

플러그인 마켓플레이스는 clone 없이 깔리고 스코프까지 골라주지만 Claude Code 전용이다. 목표가 "쓰는 에이전트를 고르면 거기에 맞게 깔린다"였는데, `npx skills` (vercel-labs/skills)가 에이전트 75종을 지원하면서 이 요건을 그대로 만족한다. 설치할 때 에이전트와 스코프를 물어보고, GitHub을 레지스트리처럼 직접 읽어서 clone도 필요 없다.

에이전트별 설치 위치:

| 에이전트 | `-a` 값 | 프로젝트 | 전역 |
| --- | --- | --- | --- |
| Claude Code | `claude-code` | `.claude/skills/` | `~/.claude/skills/` |
| Gemini CLI | `gemini-cli` | `.agents/skills/` | `~/.gemini/skills/` |
| Codex | `codex` | `.agents/skills/` | `~/.codex/skills/` |
| Cursor | `cursor` | `.agents/skills/` | `~/.cursor/skills/` |

`.claude-plugin/` 매니페스트는 나중에 얹을 수 있다. `npx skills` 가 그 매니페스트도 읽으므로 둘은 충돌하지 않는다. 마켓플레이스 자동 업데이트나 `bin/` PATH 등록이 필요해지면 그때 추가한다.

## 2. 스킬은 3개로 나눈다

하나의 스킬 안에서 분기하지 않는다.

스킬 본문은 한 번 로드되면 그 턴이 끝날 때까지 컨텍스트에 남는다. 한 스킬에서 라우팅하면 쓰지도 않는 분기의 지시문까지 매번 같이 실린다. 나누면 스킬마다 `description` 이 따로 붙어서 자동 호출 정확도도 올라간다.

## 3. 스킬 이름에 접두어를 직접 넣는다

`weekly-report`, `weekly-report-onboard`, `weekly-report-repos`.

`/weekly-report:onboard` 같은 콜론 네임스페이스는 Claude 플러그인만의 기능이다. 다른 에이전트에서는 디렉토리 이름이 곧 명령 이름이라, 접두어 없이 `onboard` 로 두면 다른 스킬과 충돌한다.

## 4. 실행은 uvx로 git에서 직접 가져온다

```
uvx --from git+https://github.com/mjkimR/weekly-report@v0.2.0 weekly-report run --json
```

설치 단계가 없고, 경로에 의존하지 않는다. `${CLAUDE_PLUGIN_ROOT}` 나 `${CLAUDE_SKILL_DIR}` 은 Claude Code 밖에서 치환되지 않는다. 게다가 스킬의 절대 경로를 모델에 알려주는 방식이 에이전트마다 달라서, 스킬이 자기 위치를 알아내는 식으로 짜면 쉽게 깨진다. uvx로 가면 그 문제가 아예 생기지 않는다.

스킬 디렉토리에는 마크다운만 둔다. 파이썬 코드는 git 태그에서 가져오고, 태그는 `SKILL.md` 에 박아둔다. `npx skills update` 로 새 `SKILL.md` 가 오면 코드 버전도 함께 올라가므로 둘이 어긋나지 않는다.

검토한 대안:

- `uv tool install` — PATH를 건드리고 업데이트를 따로 관리해야 한다.
- `uv run --project` + `UV_PROJECT_ENVIRONMENT` — 잘 동작하지만 플러그인 경로 변수에 의존해서 Claude 전용이 된다.
- 스킬 안에 스크립트를 넣기 — 스킬이 자기 경로를 알아내야 한다.

## 5. 설정과 상태는 한 디렉토리에 모은다

`~/.weekly-report/` 아래에 `config.yaml`, `template.md`, `report.md`, `history/` 를 전부 둔다. `WEEKLY_REPORT_HOME` 으로 바꿀 수 있다.

XDG 규약대로 설정은 `~/.config/`, 상태는 `~/.local/state/` 로 쪼개는 안을 먼저 검토했다가 접었다. 손으로 여는 파일이 `config.yaml`, `template.md`, `report.md` 셋인데, 이게 두 디렉토리로 갈리면 매번 어느 쪽이었는지 헷갈린다. 표준을 지켜서 얻는 것보다 "한 곳만 기억하면 된다"가 이 도구에는 더 중요하다.

핵심은 프로젝트 트리 밖에 둔다는 점이다. 그래서 `.gitignore` 문제가 사라지고, 스킬을 프로젝트 스코프로 깔아도 산출물이 저장소에 섞이지 않는다. Claude 플러그인의 `${CLAUDE_PLUGIN_DATA}` 는 다른 에이전트에서 쓸 수 없어서 후보가 아니다.

## 6. 결과는 파일 경로만 알려준다

에디터로 자동 실행하지 않고, 리포트 본문을 대화창에 쏟지도 않는다. 절대 경로를 출력하고 끝낸다.

`open -a` 로 에디터를 띄워주는 안도 검토했지만, PyCharm과 VS Code 터미널 모두 경로를 클릭하면 바로 열려서 접었다. 굳이 대신 열어줄 이유가 없다.

수정도 사용자가 직접 한다. 리포트에는 커밋에서 알아낼 수 없는 항목(`할 일` 같은 것)이 있어서 결국 매주 손을 보게 되는데, 그 수정을 대화로 지시하는 것보다 파일을 열어서 고치는 쪽이 빠르다.

## 7. 작업 파일 이름을 고정한다

`report-20260730-091331.md` 처럼 타임스탬프를 붙이지 않고 `report.md` 로 둔다. 다음 실행 때 `history/report-<날짜>.md` 로 옮긴다.

파일 이름이 매주 바뀌면 에디터 탭도 최근 파일 목록도 그때마다 무효가 된다. 이름을 고정하면 탭 하나를 열어둔 채로 계속 쓸 수 있다.

## 8. 이름을 `weekly-report` 로 통일한다

저장소, 패키지, 콘솔 스크립트, 모듈, 스킬 이름을 모두 맞춘다. 모듈 디렉토리는 `weekly_report`.

원래 이름 `weekly-report-prompt` 는 프롬프트를 만들어 주는 도구였을 때는 맞았지만, 이제 프롬프트 생성은 내부 구현이고 사용자가 받는 것은 주간보고다. 저장소 이름은 설치 명령에 그대로 노출된다.

```
npx skills add mjkimR/weekly-report
uvx --from git+https://github.com/mjkimR/weekly-report@v0.2.0 weekly-report
```

`--from` 뒤에 오는 저장소와 그 뒤의 스크립트 이름이 같아서 읽기 편하다. GitHub이 이름 변경 후 옛 URL을 영구 리다이렉트하므로 `v0.1.0` 을 가리키는 참조는 계속 동작한다. `PromptGenerator` 클래스 이름은 그대로 둔다. 내부적으로는 여전히 프롬프트를 만드는 게 맞다.

## 9. `repository` 를 객체 목록으로 바꾼다

```yaml
author: minjae.kim

repository:
  - path: /Users/mj/workspace/athena
    name: Athena
    authors: [minjae.kim, mjkim]
```

문자열 목록으로 뒀을 때 걸리는 게 두 가지였다. 표시 이름이 경로의 마지막 조각으로 고정돼서 `athena` 밖에 못 썼고, `author` 가 전역 하나뿐이라 저장소마다 커밋 이름이 다르면 조용히 0건이 됐다. `authors` 를 저장소별 목록으로 두면 둘 다 풀린다.

문자열 목록은 하위 호환으로 받지 않는다. 어차피 호환을 깨는 릴리스이고 사용자가 한 명이라, 변환 절차를 [migration.md](migration.md) 에 적어두는 쪽이 깔끔하다.

## 10. 설정 형식은 YAML을 유지한다

`tomllib` 이 표준 라이브러리라 TOML로 옮기는 안을 검토했다. 옮기면 `pyyaml` 하나는 빠지지만 다른 의존성이 남는 한 의존성을 관리해야 하는 상황은 그대로다. 설정 형식을 갈아엎을 만한 이득이 아니다.

`rich` 와 `tiktoken` 은 뺀다. 출력을 읽는 쪽이 사람이 아니라 에이전트라서 패널과 표는 파싱을 방해하는 잡음이고, 토큰 수는 경고용 어림값이라 `len(text) // 4` 로 충분하다. 이미 그 폴백이 들어 있다. `gitpython`, `pydantic`, `pyyaml` 은 남긴다.

의존성을 완전히 걷어내려면 표준 라이브러리만 쓰도록 고쳐야 한다. 그런데 macOS 기본 파이썬이 3.9라서 그렇게 해도 결국 uv가 파이썬을 받아와야 한다. 들이는 공에 비해 남는 게 없다.

## 11. 프롬프트는 고정 이름 파일로 넘긴다

`~/.weekly-report/prompt.md` 에 쓰고 매 실행마다 덮어쓴다. `--json` 출력에 경로를 담는다.

처음에는 프롬프트 파일을 아예 두지 않고 JSON 안에 문자열로 넣으려 했다. 그런데 프롬프트가 수만 토큰짜리다. JSON에 넣으면 이스케이프 때문에 에이전트가 읽기 어려워지고, 문제가 생겼을 때 눈으로 확인할 것도 남지 않는다. 파일로 두면 에이전트는 그냥 읽으면 되고 디버깅도 쉽다.

타임스탬프를 붙이지 않으므로 파일이 쌓이지 않는다. 사용자가 관리할 산출물이 아니라 실행 중간 산물이다.

## 12. 전환은 이 저장소에서 진행한다

별도 저장소를 만들지 않는다.

설치 경로 두 개가 같은 저장소 URL을 가리켜야 한다. `npx skills add mjkimR/weekly-report` 는 `SKILL.md` 를 찾고 `uvx --from git+.../weekly-report` 는 파이썬 패키지를 가져온다. 저장소를 쪼개면 고정할 버전이 둘로 늘어나서, 태그 하나로 스킬과 코드를 맞추려던 장치가 무력해진다.

남은 작업도 새로 쓰는 코드가 아니라 기존 파일 수정이다. `v0.1.0` 태그를 먼저 찍어두면 전환 전 상태가 그대로 보존되고 `uvx ...@v0.1.0` 으로 실행도 된다.

## 13. 호환을 깨는 변경은 v0.2.0 하나로 묶는다

설정 형식, 설정 위치, `repository` 스키마, CLI 하위 명령, 이름 변경이 모두 호환을 깬다. 나눠서 내면 중간 버전마다 마이그레이션이 필요해진다.

## 14. `memo.md` 를 없앤다

자유 메모 파일과 그것을 프롬프트에 끼워 넣는 단계를 모두 뺀다.

메모는 CLI 도구였을 때의 장치다. 프롬프트를 파일로 받아 직접 붙여넣던 구조에서는 "이번 주에 이것도 반영해달라"를 전할 통로가 파일밖에 없었다. 스킬로 오면 그 통로가 대화 자체다. 특이사항이 있으면 스킬을 부를 때 같이 말하거나 붙여넣으면 되고, 에이전트는 이미 그 발화를 보고 있다.

파일을 유지하면 오히려 손이 더 간다. 미리 열어서 적어두고, 실행 뒤에 비우는 것을 기억해야 한다.

대신 포기하는 것이 하나 있다. 주중에 떠오른 것을 적어뒀다가 주말에 쓰는 비동기 메모가 사라진다. 그 시점에 세션이 없으면 남길 곳이 없다. 그런 용도가 필요해지면 메모 파일을 되살리는 것보다 `template.md` 처럼 사용자가 관리하는 별도 파일을 프롬프트에 붙이는 쪽을 먼저 검토한다.
